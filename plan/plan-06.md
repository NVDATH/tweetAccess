# plan-06: handoff (tweetAccess)

ต่อจาก plan-05 (ใช้แทน plan-05 ได้เลย ไม่ต้องอัปโหลด plan-05 ซ้ำ) แยก "ยืนยันแล้ว" กับ "เดา/ยังไม่ยืนยัน" ไว้ชัดเจน

## งานแรกของแชทหน้า

1. **รอบ C** (ผู้ใช้ยืนยันแล้วว่าอยู่ในเวอร์ชันแรกก่อน release ให้ทำให้เสร็จรอบเดียว ไม่ต้องรอ) รายละเอียดอยู่หัวข้อ "รอบ C" ด้านล่าง
2. ก่อนเริ่มรอบ C ขอให้ผู้ใช้กด Settings > Diagnostics > Run probe (เลือกเฉพาะส่วนอ่านอย่างเดียว) แล้วแปะรายงาน เพราะในแชทก่อนยังไม่มีรายงาน probe รอบล่าสุดของ Users and relations, Pinned tweets, Trends, People search, DM
3. ขอผลเรื่อง Notifications โหลดซ้ำหลังเที่ยงคืน (ดูหัวข้อ "รอ")

## สถานะ: ยืนยันแล้ว (ผู้ใช้ทดสอบ หรือรายงานตัวตรวจในตัวออกมาผ่าน)

### ที่เพิ่มในแชทที่แล้ว

- **tray icon:** แก้ที่ต้นเหตุแล้ว ไม่เคยเกิดซ้ำหลัง patch (overlay `StrayTrayFocusGuard` ใน tray.py ทิ้งเหตุการณ์โฟกัสที่ Explorer ยิงเอง ผ่าน `shouldAllowUIAFocusEvent`) สรุปส่งต่อ NVSky แล้ว
- **เรียง filter ใน search ด้วย Shift+ลูกศร:** ช่อง Include และ Leave out แยกลำดับกันอิสระ เก็บต่อบัญชี (`search_filter_order`, `search_omit_order`) ผู้ใช้ผ่านการลงรอบนี้แล้ว ส่วนการใช้ค้นหาจริงผู้ใช้จะแจ้งเมื่อเจอบั๊ก
- **หน้า Shortcuts (keymap):** `keymap.py` ไฟล์ใหม่ ใช้ร่วมทุกบัญชี เก็บ JSON เฉพาะคีย์ที่ต่างจากค่าเริ่มต้นในฐานร่วม (meta key `keymap`) ตารางคีย์อยู่ที่ `_DEFS` (id, ค่าเริ่มต้น, พื้นที่, ตายตัวหรือไม่) พื้นที่มี window, tab, compose, details คีย์ในหน้าต่างหลักและแท็บชนกันได้ตรวจข้ามกัน
  - ยืนยัน: เปลี่ยนคีย์ได้ (ผู้ใช้ทดสอบกับ Download), คีย์เดิมเลิกทำงาน, ป้ายตามคีย์, หน้าต่างรอกดคีย์รับ Alt+ตัวอักษร, ชื่อหน้าต่าง Settings ตามหมวด
  - ป้ายที่ติดคีย์ตามหน้า Shortcuts (ปุ่ม toolbar, เมนู Alt+A, ปุ่ม Post, หน้าต่างข้อความเต็ม) ผ่าน `keymap.with_key` และ `MainWindow.refresh_labels` (เรียกจาก `settings_changed`) ประโยคที่เคยเขียนชื่อคีย์ตายตัวตามคีย์จริง (`utils.login_needed_text`, `tabs._gap_text`, ประโยค Home ว่าง) ลงแล้ว ผู้ใช้ไม่ได้ทดสอบประโยคเหล่านี้ทีละข้อ (ตัวตรวจในตัวไม่ครอบคลุมประโยค)
  - action ที่เพิ่มใหม่ต้องใส่ครบ 4 ที่: `_DEFS`, `label()`, ตัวจับคีย์ของหน้าต่างนั้น, และต้องผ่านข้อตรวจ "every action is used by a window"
- **voice profile ของ auto read:** ผ่านทั้งโหมด main เปิดและปิด รวมกรณี synth ต่างกัน (กรณีหลักที่ผู้ใช้ต้องการ) การขัดด้วยคีย์ยังหยุดได้ทั้งสองโหมด ค่าเก็บต่อบัญชีที่ `auto_profile` เลือกในหน้า General (แนวเดียวกับของ NVSky: trigger ส่วนตัว `tweetAccessAutoRead`; โหมด main เปิดใช้การเปิดโปรไฟล์ค้างไว้ทั้งรอบ ไม่ห่อรายแถว) autoread.py ฝั่งเราไม่เหมือนของ NVSky แล้ว ผู้ใช้ตัดสินใจไม่ต้อง sync ให้แลกเปลี่ยนกันทีละน้อย
- **B3 ตรวจเบื้องหลังหลายบัญชี:** บัญชีที่ 2 (เปิดช่อง Enable in background) ทำงาน ได้ยินข้อความชื่อแท็บ unread ถูกต้อง
  - `FetchService`: งานเดียวต่อครั้ง ใช้ `submit(..., background=True)` สำหรับงานเบื้องหลัง งานของผู้ใช้เข้าคิวหลังงานเบื้องหลังที่กำลังรันได้ แต่งานเบื้องหลังไม่เข้าคิว เก็บ client ต่อบัญชี (`_clients`)
  - ตัวตั้งเวลา: ตาราง `_bg_due` คีย์ `(account id, item)` โดย item คือ `home`, `notifications`, `bookmarks` หรือ `"<type>:<key>"` ของแท็บที่เปิด (user, search, list, thread, quotes) งานที่เลยกำหนดนานสุดไปก่อน `GlobalPlugin._collect_due` เลือกคิว ตรวจด้วยตัวตรวจในตัวแล้ว
  - ข่าวและข้อผิดพลาดของบัญชีที่ไม่ active นำหน้าด้วย @handle (`_tag`) ตามการตั้ง Speak ของบัญชีนั้นเอง ผลลัพธ์ของบัญชีที่ถูกลบไปแล้วถูกทิ้ง (`_account_exists`) เพื่อไม่ให้ไฟล์ของบัญชีนั้นถูกสร้างกลับ
  - ตัวเลข unread ในเมนูบัญชี (Alt+W, เมนู tray) รวมทุกแท็บที่บัญชีนั้นตั้งให้ tray นับ (`_tray_counts(aid=...)`) tray แสดงเฉพาะบัญชีที่ active ข้อความไม่มีชื่อบัญชี (ผู้ใช้ตั้งใจให้สั้น)
- **หน้า Settings > Updates:** ลิสต์ติ๊ก Speak ของแท็บจริงที่เปิดอยู่ + ช่องเลือก interval แยกต่อชื่อแท็บ + ค่ากลางของ "New tabs" แท็บที่ไม่เคยตั้งเองตามค่ากลาง (ผู้ใช้ทดสอบเพิ่ม/ลบแท็บแล้วแสดงผลถูกต้อง) ค่าเก็บที่ `bg_tab_settings` (JSON `{"<type>:<key>": [minutes, speak]}` เฉพาะแท็บที่ต่างจากค่ากลาง), `bg_interval_tabs` (ค่ากลาง), `bg_announce_off` (หมวด home/notifications/tabs) ผ่าน `Config.tab_setting(ident)`
  - พฤติกรรมที่เปลี่ยนจาก plan-05: แต่ละแท็บมีรอบตรวจของตัวเอง (เดิมหมุนตรวจทีละแท็บในรอบเดียว) ยิ่งแท็บเยอะคำขอต่อ X ยิ่งมาก ต้องบอกใน README
- **Notifications id (บั๊กโหลดซ้ำ):** ยืนยันจาก log ว่า X ให้ id ของข่าวเดิมไม่เท่ากันในการดึงต่างรอบ (เวลามิลลิวินาทีเท่ากัน เลขสามหลักท้ายต่าง) ทำให้ทุกรอบดึงเห็นเป็นข่าวใหม่ทั้งหน้า แก้โดย `utils.notification_id(stamp_ms, handle, url)` ไม่ใช้ id ของ X และแปลงแคชเดิมหนึ่งครั้งต่อบัญชี (`tabstate._migrate_notifications`, flag `notif_ids_v2`, ยุบแถวซ้ำ เก็บเครื่องหมายอ่านแล้วและตำแหน่งที่อ่านค้าง) แถวซ้ำเก่าหายไปจริง (ผู้ใช้ยืนยัน และรายงานตัวตรวจแสดงซ้ำ 0)
- **ตัวตรวจในตัว (`diagnostics.run_selfcheck`, Settings > Diagnostics > Run self-check):** รายงานล่าสุด 14 ข้อผ่านทั้งหมด (คีย์ลัดทั้งชุดรวม event ปลอม, id ของ Notifications และการแปลงแคช, ตั้งค่า/คิวงานเบื้องหลัง, filter ใน search, ฐานข้อมูลต่อบัญชีด้วยฐานเข้ารหัสจริงในโฟลเดอร์ชั่วคราว รวมนำเข้าแถวเก่าหนึ่งครั้ง ค่าต่อบัญชี และการลบบัญชี) ท้ายรายงานมีสถานะจริง (แต่ละบัญชี, ตารางเวลาเบื้องหลัง, ตัวเลขเมนูบัญชี, ข้อความ tray, สถานะ worker) และบรรทัด `Self-check finished`
  - **วิธีทำงานที่ผู้ใช้ต้องการ:** พฤติกรรมหลังบ้านให้ยืนยันด้วยตัวตรวจนี้ ผู้ใช้กดปุ่มเดียวแล้วแปะรายงาน ส่วน UX/UI ผู้ใช้ทดสอบเองและแจ้ง รายการทดสอบมือต้องสั้น
  - เพิ่มข้อตรวจ: ฟังก์ชันซ้อนใน `run_selfcheck` เรียก `check("ชื่อ", ฟังก์ชัน)` ฟังก์ชันล้มด้วย `AssertionError` ใช้ `MemoryStore` หรือโฟลเดอร์ชั่วคราว และวัตถุปลอม (`SimpleNamespace`) เรียกเมธอดจริงของคลาสแบบ `GlobalPlugin._collect_due(fake, now)` ได้โดยไม่ต้องสร้างปลั๊กอิน
- **Home ใหญ่ทำ NVDA freeze (watchdog):** log (2807 แถว) ใส่แถวลง ListCtrl ใช้ 0.66-0.71 วินาที (สร้างข้อความ 0.24, ใส่ลิสต์ 0.41) ฐานข้อมูล 0.01 วินาที เปิด main ทั้งหมด 0.75-0.82 วินาที watchdog ขึ้น freeze เกิน 0.5 วินาที ผู้ใช้ลอง clear Home cache แล้วเปิดไวและไม่ freeze ดังนั้นจำนวนแถวมีผลจริง เวลาโตตามจำนวนแถว (ประมาณ 0.25 มิลลิวินาทีต่อแถว)
  - ผู้ใช้ปฏิเสธ patch ใส่แถวเป็นชุด (มองว่าซับซ้อนและอาจไม่ตรงจุด) ยังไม่ได้ลง ให้รอดูว่าจำนวนแถวเท่าไรเริ่มมีผล แล้ววางแผนทำ lazy load ทีหลัง และให้ไล่เช็กอีกทีตอน clean up (ที่ NVSky เคยเจออาการคล้ายกัน หายหลังปรับตรรกะและ clean up บางอย่าง)
  - อาการไม่แน่นอน (บางรอบเปิดไว) log ที่ได้ไม่ได้จับรอบที่ช้ากว่านี้

### ของเดิมจาก plan-05 (ย่อ ยืนยันแล้ว)

- **ฐานข้อมูลต่อบัญชี:** `Store` เป็นตัวหน้า (facade) ฐานร่วม `tweetaccess.db` เก็บรายชื่อบัญชี cookie บัญชีที่ active ธง `bg_enabled:<id>` และค่ากลางรุ่นเก่า ส่วน `accounts\<id>.db` เก็บ tweets และ meta ต่อบัญชี ใช้คีย์ไฟล์เดียวกัน ชื่อไฟล์เป็นเลข id ภายใน (ไม่ใช่ uid ของ X) ย้ายแถวเก่าเข้าไฟล์ของบัญชีครั้งเดียว (ธง `migrated_from_shared`) ลบบัญชี = ลบไฟล์
- **สลับบัญชีจุดเดียว:** `switch_account(account_id, focus=False, after_menu=False)` และ `accounts_changed(focus)` เป็นจุดเดียวที่ rebuild หน้าต่างหลัก ทุกครั้งหยุด auto read โหลดค่าของบัญชีใหม่ รีโหลด sound pack
- **เมนูบัญชี:** Alt+W ในหน้าต่างหลัก, เมนู tray เมื่อมีมากกว่าหนึ่งบัญชี เสียงประกาศหลังเมนูปิดใช้ `announce_after_menu`
- **ค่าต่อบัญชี:** `Config(store, account_id)` ทุกอย่างของหน้า General, Updates, Display, Sound แยกต่อบัญชี หน้า Accounts ใช้ร่วมกัน นำเข้าค่ากลางเดิมหนึ่งครั้ง (ธง `cfg_imported`) หน้าตั้งค่าต่อบัญชีมี `PER_ACCOUNT = True` กด Set as active ใน Settings บันทึกค่าที่พิมพ์ค้างให้บัญชีเดิมก่อนแล้วสร้างหน้าเหล่านั้นใหม่
- **หน้าต่างหลักไม่เด้งทับ Settings:** `MainWindow.rebuild` สั่ง `Disable()` ระหว่าง rebuild เมื่อไม่ได้ขอโฟกัสและหน้าต่างไม่ active (สาเหตุ: `notebook.AddPage` ใน wx ทำให้หน้าต่างที่ไม่ active ถูก activate เอง)
- **thread / quotes โหลดเพิ่ม:** F5 อ่านตาม `feed_pages`, Shift+F5 โหลดหน้าถัดไป (ประมาณ 20 ต่อครั้ง, `FetchService._chains` คีย์ `thread:<id>`, `quotes:<id>`) สาเหตุจากซอร์ส twifork 2.4.0: `get_tweet_by_id` ให้ reply หน้าแรกหน้าเดียว และ `search_tweet` ให้หน้าแรกหน้าเดียว
- **Ctrl+Shift+T คืนแท็บที่ปิด:** เก็บในหน่วยความจำ ต่อบัญชี สูงสุด 20 แท็บ (`remember_closed_tab`, `pop_closed_tab`)
- **NVDA+Shift+F5:** update Home เหมือน F5 ของ Home (คำสั่ง global ถอนได้จาก Input gestures)
- **ข้อจำกัด:** add-on รองรับ NVDA 2026.1 ขึ้นไปเท่านั้น (ไม่รองรับ Windows 10)

## เสร็จแล้วแต่ยังไม่ยืนยันทีละข้อ / ค้างทดสอบ

1. **เพิ่มและลบบัญชีใน Settings (ส่วน UI):** หน้าอื่นต้องสร้างใหม่ถูก ไม่มี error (ส่วนข้อมูลของการลบบัญชียืนยันแล้วด้วยตัวตรวจในตัว)
2. **sound pack กับรูปแบบข้อความ tray แยกตามบัญชี:** ผู้ใช้ติดไว้ (sound pack default ยังทำไม่เสร็จ) ค่าแยกต่อบัญชียืนยันแล้วด้วยตัวตรวจ ที่เหลือคือส่วนเสียงจริง
3. ประโยคที่ตามคีย์จริง (Home ว่าง, ช่องว่างหลัง refresh, ข้อความยังไม่ล็อกอิน) ยังไม่ได้ทดสอบทีละข้อ
4. การตรวจครั้งแรกของบัญชีอื่นหลังเปิด NVDA ต้องรอครบรอบ interval (รายงานแสดง client ที่เก็บไว้เฉพาะบัญชี active) การซิงก์ตอนเริ่ม (15 วินาที) ยังทำเฉพาะบัญชี active ผมเสนอไว้แล้วว่าถ้าอยากให้ตรวจเร็วขึ้นหลังเปิด ให้บอก ผู้ใช้ยังไม่ได้ตอบ

## รอ / ค้างติดตาม (ยังไม่ยืนยันสาเหตุหรือผล)

1. **Notifications โหลดซ้ำหลังเที่ยงคืน:** สมมติฐาน (ยืนยันจาก log ว่าเป็นสาเหตุของการซ้ำที่เห็น) คือ id ของ X ไม่นิ่ง และตอนนี้ id ไม่ขึ้นกับมันแล้ว แต่ยังไม่ยืนยันว่า bgsync หลังเที่ยงคืนหายซ้ำจริง ต้องรอวันใหม่ ถ้ายังซ้ำ ให้ขอบรรทัด `TEMP notif` ล่าสุด (ถ้า "twin" ยังมี id ไม่เท่ากัน แปลว่าส่วนไหนของสูตร `author|url` ยังไม่นิ่ง)
2. **Home ใหญ่:** ดูหัวข้อด้านบน รอดูขนาดที่เริ่มมีผล แล้วค่อยออกแบบ lazy load หรือการตัดแถวเก่า (การตัดแถวที่อ่านแล้วและเก่า เป็นการตัดสินใจของผู้ใช้ ยังไม่ได้ถาม)
3. ข้อที่ยังไม่ยืนยันเดิมจาก plan-05: เสียง Network ตอน bgsync ขณะอยู่แอปอื่น (เชื่อว่าแก้แล้ว) ถ้าเกิดอีกให้เปิด debug logging ดูบรรทัด "dropped a focus event"; Thread เปิดแล้วเงียบ (ไม่พบอีก); quick action หน่วงเล็กน้อย (ไม่ใช่บั๊ก); ตัวกรองของ operator `quoted_tweet_id:` ยืนยันแล้ว ส่วน operator อื่นยังไม่ยืนยัน

## รอบ C (งานแรกของแชทหน้า ผู้ใช้ยืนยันว่าอยู่ก่อน release)

ส่งเป็นรอบย่อยที่ทดสอบได้ทีละอย่าง ใช้ตัวตรวจในตัวแทนรายการทดสอบมือสำหรับส่วนหลังบ้าน ก่อนเขียนทุกฟีเจอร์ให้ดูรายงาน probe (หัวข้อ "งานแรก" ข้อ 2) ลำดับที่เสนอ (ยังเป็นข้อเสนอ ผู้ใช้ยังไม่ได้ตัดสินลำดับ):

1. **เมนูผู้ใช้ (Alt+U) และ pinned tweet:** ตอนนี้ Alt+U (`user_timeline`) เปิด timeline ของผู้ใช้โดยตรง ต่อไปเป็นเมนูผู้ใช้ (ข้อมูลผู้ใช้, timeline, pinned tweet, follow/unfollow, mute, block และ action อื่นที่ probe ยืนยัน) ข้อมูลจาก probe ที่มีมาแล้ว: `get_user_by_screen_name` ให้ฟิลด์ `following`, `followed_by`, `blocking`, `muting`, `can_dm`, `protected`, `verified`, `followers_count`, `pinned_tweet_ids` (ฟิลด์เหล่านี้อยู่ในรายการที่ probe อ่าน แต่ผลจริงยังต้องดูจากรายงาน) `get_tweet_by_id` ใช้กับ id ที่ปักหมุด; ห้ามใช้ `get_user_by_id` และ `client.user()` (ได้ 403)
   - action ที่เขียนบัญชี (follow, mute, block) เสี่ยงต่อบัญชี ให้ทำแบบมีกล่องยืนยันและตัวเลือกปิดได้ และบอกผู้ใช้ก่อนว่าจะทำอะไร
2. **แท็บ Explore:** trends (`get_trends(category)` ที่ probe ลอง: trending, for-you, news, sports, entertainment), trends ตามสถานที่ (`get_available_locations`, `get_place_trends(woeid)`), ค้นหาคน (`search_user`) ใช้โครงแท็บเสริมเดิม (`OPTIONAL_TAB_CHOICES`, `tabs_off`) และเข้าระบบ Updates ได้ถ้าเหมาะสม
3. **แนบสื่อในหน้าเขียนทวีต:** `upload_media(path, wait_for_completion=True)` + `create_media_metadata(media_id, alt_text=...)` + `create_tweet(media_ids=[...])` ย่อรูปด้วย Pillow (Pillow ที่มากับ NVDA มีอยู่ ใช้อยู่แล้วใน `attachments._webp_to_png`) สูงสุด 4 รูปหรือ 1 วิดีโอ/GIF ต้องมี alt text ได้ ใส่ action ใหม่ในพื้นที่ compose ของ keymap probe ส่วนทดสอบสื่อ (`media_tests`) มีอยู่แล้วใน diagnostics.py ใช้ยืนยันก่อน
4. **DM (ทำเท่าที่ไม่เสี่ยงเกินไป ตามที่ผู้ใช้สั่ง):** inbox ยืนยันแล้ว (plan-05) ที่เหลือคือ `get_dm_history` กับบทสนทนาจริงและข้อความที่เข้ารหัส ให้เริ่มจากอ่านอย่างเดียว ส่วนส่งข้อความ (`send_dm`) เสี่ยงต่อบัญชีมากที่สุด ต้องถามผู้ใช้ก่อนเขียน
5. **ประเมิน endpoint อื่นที่ยังไม่ได้ลอง:** `search_tweets_by_date`, `get_user_highlights_tweets`, `get_user_subscriptions`, `get_user_spotlights`, `get_user_mentions`

## เก็บกวาดก่อนปล่อย

1. **ลบ TEMP ทั้งหมด** (ดูรายการด้านล่าง) หลังยืนยัน Notifications หลังเที่ยงคืนและไล่เรื่อง Home freeze แล้ว
2. **Home freeze:** ไล่เช็กอีกทีตอนนี้ (ตามที่ผู้ใช้ขอ) อาจมีส่วนที่ซ่อนอยู่ ดู log ตัวเลขเดิมเปรียบเทียบ
3. `tabs.make_temp_tab` ซ้ำโครงกับ `build_tabs` (ควรรวม) พารามิเตอร์ `index` ของ `notification_to_post` ไม่ถูกใช้แล้ว
4. แถวเก่าค้างในฐานร่วม (ตาราง tweets และ meta ต่อบัญชีรุ่นก่อน B1, ค่า cfg กลางรุ่นก่อน B2c) ลบด้วยโค้ดแยก + VACUUM (ผู้ใช้ยังไม่ได้สั่ง ควรรอใช้งานจริงสักระยะ)
5. สตริงใหม่ตั้งแต่ B2b จนถึงตอนนี้ต้องรวมเข้าไฟล์แปลก่อนปล่อย แต่ **ยังไม่มีไฟล์แปลและโปรเจกต์ยังไม่ publish** จึงเปลี่ยน msgid ได้อิสระจนกว่าจะปล่อย (มี `# Translators:` ครบแล้ว ยกเว้น diagnostics.py ที่ไม่แปลและไม่แจกในรุ่นปล่อย)

## README ที่ต้องเขียน (ทำท้ายสุด)

- คำเตือนความเสี่ยงตามเดิม: endpoint ภายใน (ผิดข้อกำหนดของ X), หลายบัญชีจาก IP เดียว, rate limit, Shift+F5 สำหรับช่องว่างใหญ่ และการตรวจเบื้องหลังหลายบัญชี/หลายแท็บเพิ่มจำนวนคำขอ (ชี้ให้ปรับ interval ที่หน้า Updates)
- ต้องใช้ NVDA 2026.1 ขึ้นไป
- **วิธีสร้าง profile สำหรับเสียง auto read คร่าว ๆ (ผู้ใช้สั่งให้ใส่):** ในเมนู NVDA เปิด Configuration profiles สร้างโปรไฟล์ใหม่ ตั้งการเปิดใช้เป็นแบบ manual เท่านั้น (ไม่ผูกกับแอปหรือเหตุการณ์) เปิดโปรไฟล์ไว้ ปรับ synthesizer กับเสียงใน Speech settings (กรณีหลักคือใช้ synthesizer ตัวอื่นจากปกติ) ปิดโปรไฟล์ แล้วเลือกใน Settings > General > Auto read voice profile ของ add-on (ก่อนเขียนจริงตรวจชื่อเมนูกับตัวเลือกให้ตรงกับ NVDA รุ่นที่รองรับ)
- วิธีส่งออก cookie (ส่วน Add account), หน้า Shortcuts (ใช้ร่วมทุกบัญชี), หน้า Updates (ค่า "New tabs" และแท็บที่ตั้งเอง), ค่าต่อบัญชี
- Known issues (ตัดสินใจแล้วใน plan-05 ยังใช้):
  - *Auto read with the main window open reads each row as NVDA does, so "Read the whole message of long tweets" only applies when the main window is closed.* (ข้อความเดิมของ auto_full)
  - จำนวนใน thread/quotes ไม่ตรงกับตัวเลขใน tweet info เสมอ (X ซ่อน reply/quote บางส่วน reply count นับเฉพาะ reply ตรง ๆ ส่วน thread รวมทวีตต้นทางและ reply ซ้อน เหตุผลของ "ไม่ตรง" เป็นการเดาจากพฤติกรรม)
  - F5 และ sync เบื้องหลังในแท็บ thread/quotes อ่านใหม่ตาม `feed_pages` ถ้าโหลดเพิ่มด้วย Shift+F5 ไปไกลกว่านั้น รายการจะย่อกลับ
  - แท็บที่ปิดแล้วคืนได้ด้วย Ctrl+Shift+T เฉพาะในรอบ NVDA ที่เปิดอยู่
  - เลือกหลายแถวแบบไม่ติดกันทำไม่ได้ (Ctrl+A และ Shift+ลูกศรเลือกหลายแถวได้ ใช้กับ Mark as read/unread ในเมนู Alt+A)
  - Home ที่มีหลายพันแถวทำให้การเปิดหน้าต่างหลักช้า (ถ้ายังไม่ได้ทำ lazy load)
  - (ตัดทิ้ง) ข้อ "Enable in background มีผลเฉพาะบัญชี active" ไม่จริงแล้วหลัง B3

## รายการ TEMP (ติดป้าย `# TEMP` ทุกบรรทัด ลบทีหลัง)

- **service.py:** ในเมธอด `_convert` สามบรรทัดที่เก็บ id ดิบ (`raw = getattr(self, "_notif_raw", None)` ... `raw.setdefault(...)`), เมธอด `_log_notification_diff` ทั้งก้อน, ใน `_feed` บรรทัด `self._notif_raw = ...` และสองบรรทัดที่เรียก `_log_notification_diff`
- **feedlist.py:** `import time`, ใน `_set_row` ตัวจับเวลา (`t0`, `t1`, `_t_texts`, `_t_wx`), ใน `_add_posts` (`started`, `_t_texts`/`_t_wx`, `t_status`, บล็อก `log.info` ที่ติด `# TEMP` ท้ายบล็อก), ใน `on_clock_timer` (`started` และบล็อก log)
- **tabs.py:** `import time`, ใน `HomePanel.load_cached` (ตัวจับเวลาและ `log.info`), ใน `build_tabs` (`t_start`, `t_add`, และ `log.info` ท้ายเมธอด)
- **core.py:** ใน `_open_main` (ตัวจับเวลาและ `log.info`), ใน `tray_refresh` (`t0` และ log), ใน `_on_bg_tick` (`tick_start` และบล็อก `finally`) หมายเหตุ: `import time` ของ core.py เป็นของเดิม ห้ามลบ
- บล็อก `log.info(` หลายบรรทัดจะติด `# TEMP` เฉพาะบรรทัดปิด ตรวจให้ลบทั้งบล็อก

## ข้อสังเกตที่ควรจำ

- **รูปแบบ patch (ผู้ใช้เข้มงวดมาก ห้ามปรับรูปแบบเอง):** ชื่อไฟล์กำกับก่อนทุก code block, หนึ่ง fence มี `old_str:` และ `new_str:` ครบคู่ (ห้ามแยกสอง fence ห้ามรวมสองจุดแก้), `old_str` มี context ที่ไม่ซ้ำทั้งไฟล์, แก้เกิน 1-2 บรรทัดให้ส่งทั้งเมธอด, โค้ดและ log เป็นภาษาอังกฤษ, control ใหม่ใน wx มี mnemonic (ยกเว้นป้ายที่ใส่คีย์ลัดและรายการไดนามิกจากชื่อแท็บ), สตริงผู้ใช้เห็นครอบด้วย `_()` พร้อม `# Translators:` ยกเว้น diagnostics.py กับ autoread.py, log ชั่วคราวติด `# TEMP` ทุกบรรทัด, จบด้วย "ที่ต้องทดสอบ" (ตอนนี้ให้สั้นและใช้ตัวตรวจในตัวแทนส่วนหลังบ้าน)
- ผู้ใช้ไม่ต้องการ patch ซับซ้อนเกินจำเป็น: ถ้าผู้ใช้บอกว่าวิธีซับซ้อนและน่าจะแก้ไม่ตรงจุด (เช่น patch ใส่แถว Home เป็นชุด) ให้เสนอให้ง่ายก่อน หรือเก็บไว้ตอน clean up
- ผู้ใช้ไม่ต้องการ patch สำหรับการแก้ตัวเลขแถวเดียว บอกว่าแก้ที่แถวไหนพอ ผู้ใช้ไม่ต้องการให้ไล่อ่านของเก่า ผู้ใช้สำรองไฟล์ก่อนทดลอง patch เสี่ยง และถอนเองได้
- แยก "ยืนยันแล้ว" กับ "เดา" เสมอ ชี้หลักฐานจาก log/โค้ด ผู้ใช้ไม่ต้องการให้คาดหวังว่ารอบไหนจะผ่าน
- **เมธอดของคลาสแม่ vs attribute:** ห้ามตั้ง attribute ชื่อเดียวกับเมธอดของ `TweetPanel` (กรณี `_target`) ตรวจชื่อก่อนเพิ่มด้วย grep ทั้งโปรเจกต์ ชื่อที่เพิ่มรอบนี้ (ผ่านการตรวจชน): `_KEY_ACTIONS`, `_LIST_ONLY`, `_do_mark_read`, `_do_mark_unread`, `_do_mark_all`
- **wx:** `AddPage` ของหน้าต่างที่ไม่ active ทำให้ activate หน้าต่างนั้น ต้องกันด้วย `Disable()` ระหว่างสร้าง; ListCtrl ใส่แถวทีละแถวใช้ประมาณ 0.25 มิลลิวินาทีต่อแถวบน thread เดียวกับ NVDA และ watchdog ของ NVDA รายงาน freeze เมื่อค้างเกิน 0.5 วินาที; ตัวจับคีย์ `EVT_CHAR_HOOK` ของแท็บทำงานก่อนของหน้าต่างหลัก คีย์ที่แท็บไม่รับต้อง `Skip()`
- **NVDA:** ลำดับเหตุการณ์โฟกัส UIA → `shouldAllowUIAFocusEvent` → `queueEvent` → `executeEvent` → `doPreGainFocus` (อาจเรียก `foreground` ซึ่งสั่ง `cancelSpeech`) → `event_gainFocus` ของ plugin การกลบใน plugin จึงช้าเกินไป
- **X:** id ของ notification ไม่นิ่งระหว่างการดึง ห้ามใช้ id ดิบมาเป็นตัวระบุ; `get_user_by_id` และ `client.user()` ได้ 403; X ตอบช้าเป็นช่วง ๆ (ReadTimeout ไม่ได้แปลว่าเมธอดพัง)
- **twikit/twifork:** `get_tweet_by_id(tweet_id, cursor=None)` คืน reply หน้าแรก (`tweet.replies` เป็น `Result` ที่มี `next()`) `search_tweet(count<=20)` คืนทีละหน้า
- การแปลงแคชเก่าทำที่ `tabstate.get_cache` เมื่ออ่านแคช Notifications ครั้งแรกของบัญชี ไม่ใช่ตอนเปิด NVDA
- ค่าที่ผู้ใช้ตั้งไว้ในช่องเดิม (interval ของ Home, Notifications, Bookmarks และของแท็บ) ถูกอ่านต่อโดยหน้า Updates ไม่ต้องย้ายค่า
